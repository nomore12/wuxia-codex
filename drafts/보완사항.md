# 저장소 구조 보완 사항

이 문서는 현재 구조의 장점을 유지하면서, 세력과 작업 차수가 늘어날 때 생길 수 있는 혼선을 줄이기 위한 제안이다.

여기에 적힌 내용은 아직 정전이나 작업 규칙이 아니다. 실제 적용 시에는 항목별로 작성자 승인을 받은 뒤 관련 문서와 스크립트를 함께 변경한다.

## 검토 결과 — 1차 완료 시점

| 항목 | 판정 | 왜 |
|---|---|---|
| 1. 색인을 indexes/로 | **보류** | 지금 색인은 전부 초안이라 `source_status`가 균일하다. 세력 문서를 정전으로 승격하기 시작할 때 적용한다 |
| 2. status/phase 분리 | **채택, 축소** | `phase`는 3차 진입에 필요하다. **`review`는 도입하지 않는다** — 작성자가 채팅에서 검토하므로 아무도 갱신하지 않는 필드가 된다 |
| 3. 차수별 규칙 | **채택, 축소** | **2차 규칙은 필요 없다.** 1차 작업 중에 중복·origin·오류 정리가 모두 끝났다. 3차·4차 규칙만 작성한다 |
| 4. 진행현황 자동화 | **보류** | 1차가 44/44로 끝나 지금은 셀 것이 없다. 3차가 진행되면 다시 본다 |

> 이 판정은 1차 완료 시점의 것이다. 상황이 바뀌면 다시 본다.
> 처음 이 문서를 검토했을 때(1차 진행 중)는 네 항목이 전부 보류였다.
> 스키마를 바꾸면 남은 세력을 새 스키마로 만들다 또 고치게 되기 때문이었다.

## 1. 자동 생성 색인과 정전의 위치 분리

### 현재 상태

`canon/무공색인.md`는 `scripts/build_index.py`가 `drafts/factions/`의 문서를 읽어 자동 생성한다.

이 구조에는 두 가지 서로 다른 의미가 섞여 있다.

- `canon/`은 작성자가 승인한 사실을 보관하는 곳이다.
- `무공색인.md`는 승인 전 초안을 포함한 작업 현황을 기계적으로 모은 산출물이다.

색인의 개별 행은 초안에서 왔는데 파일의 위치와 frontmatter는 정전처럼 보인다. 따라서 사람이 색인을 설정의 근거로 잘못 사용할 가능성이 있다.

### 권장 구조

자동 생성물을 위한 `indexes/` 디렉터리를 추가한다.

```text
.
├─ canon/                         작성자가 승인한 설정
├─ drafts/                        승인 전 설정
├─ indexes/                       자동 생성한 조회용 색인
│  ├─ 무공색인.md                초안과 정전을 모두 포함한 작업용 색인
│  └─ 확정무공색인.md            확정된 세력 문서만 포함하는 색인, 필요해질 때 추가
└─ scripts/
   └─ build_index.py
```

당장은 확정된 세력 문서가 없으므로 `indexes/무공색인.md` 하나만 운용한다. 향후 확정 세력 문서를 별도로 보관하기 시작할 때 `확정무공색인.md`를 추가한다.

작업용 색인에는 각 항목의 출처 상태를 표시한다.

```markdown
| 명칭 | 한자 | origin | 세력 | sect_id | 분류 | source_status | source_path |
|---|---|---|---|---|---|---|---|
| 매화검법 | 梅花劍法 | 관용 | 화산파 | hwasan | 검법 | draft | drafts/factions/화산파.md |
```

`source_status`가 `draft`인 행은 중복 검사에는 사용하지만 정전의 근거로는 사용하지 않는다.

### 생성 규칙

- 색인은 손으로 편집하지 않는다.
- 생성 결과는 작업자와 실행 환경이 달라도 같은 결과가 나와야 한다.
- 정렬 기준을 스크립트에 고정한다.
- 색인에 있는 정보가 원본 문서와 다르면 항상 원본 문서를 우선한다.
- 생성 파일 자체에는 독립적인 설정 권한이 없다.
- 초안 명칭도 이후 작업의 중복 방지를 위해 색인에 포함한다.
- 초안이 삭제되거나 이름이 바뀌면 다음 생성 시 해당 행도 사라져야 한다.

### 적용 절차

1. `indexes/`를 만들고 기존 색인을 `indexes/무공색인.md`로 이동한다.
2. `scripts/build_index.py`의 출력 위치와 표 스키마를 변경한다.
3. `README.md`, `CLAUDE.md`, `specs/1차작업규칙.md` 등 기존 색인 경로를 참조하는 문서를 일괄 수정한다.
4. `validate.py`가 새 색인을 읽도록 변경한다.
5. `python scripts/build_index.py`로 새 색인을 생성한다.
6. 이전 `canon/무공색인.md`가 더 이상 참조되지 않는지 검색한다.
7. 전체 세력 문서 검증과 색인 최신성 검사를 실행한다.

### 완료 기준

- `canon/`에는 승인된 설정과 승인된 규칙만 남아 있다.
- 작업용 색인의 모든 행에서 원본 경로와 원본 상태를 확인할 수 있다.
- 색인을 읽는 것만으로 초안 항목을 확정 설정으로 오해할 여지가 없다.
- 기존 중복 검사와 공통 무공 감지는 그대로 동작한다.

## 2. 문서 상태와 작업 차수 분리

### 현재 상태

현재 `status`에는 `확정`, `draft`, `초안`, `1차 초안`, `수집 중`처럼 서로 다른 종류의 값이 들어간다.

- 승인 여부: 초안인가, 확정인가
- 작업 단계: 몇 차 작업까지 끝났는가
- 작업 흐름: 검토 중인가, 수집 중인가

이 세 가지를 하나의 필드로 표현하면 자동화할 때 `1차 초안`과 `초안`이 같은 권한을 갖는지 별도로 해석해야 한다.

### 권장 frontmatter

각 축을 별도 필드로 분리한다.

```yaml
---
doc_type: faction
status: draft
phase: 1
review: pending
sect_id: hwasan
depends_on:
  - canon/body-and-mind/00_INDEX.md
  - canon/세력목록.md
---
```

#### `status` — 설정으로서의 권한

| 값 | 의미 |
|---|---|
| `draft` | 승인 전이며 세계관의 사실이 아니다 |
| `confirmed` | 작성자가 승인했으며 정전으로 사용할 수 있다 |
| `generated` | 원본에서 자동 생성된 산출물이며 독립적인 권한이 없다 |

#### `phase` — 내용의 작업 단계

| 값 | 의미 |
|---|---|
| `1` | 이름, 한자, origin, 대표 항목까지 작성 |
| `2` | 중복과 오류를 정리하고 origin을 검증 |
| `3` | 한 줄 설명과 제한된 대표 초식을 작성 |
| `4` | 심·체 배치와 `traits`, `breaks_on`을 정리 |
| `complete` | 정해진 작업 차수를 모두 마침 |
| `collection` | 관계 단서처럼 종료 차수가 없는 수집 문서 |
| `not_applicable` | 색인이나 규칙처럼 차수 개념이 적용되지 않음 |

#### `review` — 검토 흐름

| 값 | 의미 |
|---|---|
| `pending` | 아직 검토하지 않음 |
| `in_review` | 작성자가 검토 중 |
| `changes_requested` | 수정 요청이 있음 |
| `approved` | 현재 단계의 결과가 승인됨 |
| `not_required` | 자동 생성물 등 별도 검토가 필요하지 않음 |

`review: approved`는 현재 차수를 통과했다는 뜻이며 `status: confirmed`와 같지 않다. 1차 결과를 승인받아도 전체 세력 설정은 여전히 초안일 수 있다.

### 상태 전이

```text
status: draft
  phase: 1, review: pending
        ↓ 검토 시작
  phase: 1, review: in_review
        ↓ 승인
  phase: 1, review: approved
        ↓ 다음 차수 시작
  phase: 2, review: pending
        ↓
  phase: complete, review: approved
        ↓ 작성자가 정전 승격
status: confirmed
```

수정 요청을 받으면 `phase`는 유지하고 `review`만 `changes_requested`로 바꾼다. 이전 단계로 되돌려야 한다면 작성자가 명시적으로 `phase`를 변경한다.

### 검증 규칙

`validate.py`에서 다음 조합을 검사한다.

- `status: confirmed`인데 파일이 `drafts/`에 있으면 오류
- `status: draft`인데 파일이 `canon/`에 있으면 오류
- `phase: 1`인데 2차 이후 필드가 들어 있으면 오류 또는 경고
- `phase: complete`인데 필수 차수 산출물이 없으면 오류
- `review: approved`인데 해당 단계 검증이 실패하면 오류
- `status: generated`인데 `generated_by`가 없으면 오류
- 허용 목록에 없는 상태값은 오류

### 이전 값의 변환안

| 기존 값 | 변환 |
|---|---|
| `status: 확정` | `status: confirmed`, `review: approved` |
| `status: 1차 초안` | `status: draft`, `phase: 1`, `review: pending` |
| `status: 초안` | `status: draft`, 작업 성격에 맞는 `phase` 추가 |
| `status: 수집 중` | `status: draft`, `phase: collection`, `review: pending` |

프로젝트가 사람에게 보이는 한국어 표현을 유지하려면 화면이나 보고서에서만 `draft → 초안`, `confirmed → 확정`으로 변환한다. frontmatter 값은 스크립트가 안정적으로 처리할 수 있도록 고정된 식별자를 사용한다.

### 적용 절차

1. 허용 상태와 전이 규칙을 작업 규칙 문서에 먼저 확정한다.
2. `validate.py`가 기존 값과 새 값을 잠시 모두 읽도록 전환 기간을 둔다.
3. 세력 초안부터 새 스키마로 변환한다.
4. 정전, 작업 규칙, 수집 문서, 생성 색인 순으로 변환한다.
5. 모든 문서가 변환되면 기존 상태값 호환 코드를 제거한다.

### 완료 기준

- `status`만 보면 해당 문서를 세계관의 사실로 사용할 수 있는지 판단할 수 있다.
- `phase`만 보면 어느 차수까지 진행됐는지 계산할 수 있다.
- `review`만 보면 다음 행동이 작성, 검토, 수정 중 무엇인지 판단할 수 있다.
- 문서 상태를 파일명이나 본문 문구에서 추측할 필요가 없다.

## 3. 2~4차 작업 규칙과 검증 기준 추가

### 현재 상태

1차 작업은 전용 규칙, 출력 형식, 금지 항목, 검증기가 갖춰져 있다. 반면 2~4차는 `specs/작업순서.md`에 한 줄씩만 정의되어 있다.

뒤 차수일수록 세계관에 미치는 영향이 크다. 특히 4차의 심·체 배치와 `traits`, `breaks_on`은 인물과 사건의 기반이 되므로 1차보다 강한 통제가 필요하다.

### 추가할 문서

```text
specs/
├─ 1차작업규칙.md
├─ 2차작업규칙.md
├─ 3차작업규칙.md
├─ 4차작업규칙.md
└─ 작업순서.md
```

각 차수 문서는 최소한 다음 절을 공통으로 갖는다.

1. 목적
2. 입력 조건
3. 반드시 읽을 정전
4. 허용되는 변경
5. 금지되는 변경
6. 출력 스키마
7. 멈추고 물어야 할 조건
8. 자동 검증 항목
9. 작성자 검토 항목
10. 다음 차수로 넘어가는 조건

### 2차 작업 규칙

> **이 절은 적용하지 않는다.** 1차 작업 중에 중복 정리·origin 검증·오류 수정이
> 모두 끝났다. `scripts/validate.py`와 `build_index.py`가 매 세력마다 돌았고,
> 창작 명칭 충돌 0건, origin 실측 보고 44건이 완료되었다.
>
> 다만 여기 적힌 「origin_source」와 「decision_note」는 3차에서 쓸 수 있다.

#### 목적

1차에서 넓게 모은 명칭을 줄이고 바로잡는다. 새로운 설정을 대량으로 추가하는 단계가 아니다.

#### 주요 작업

- 다른 세력 및 같은 문서 안의 중복 명칭 정리
- 금지 한자와 세계관 위반 명칭 제거
- `origin`을 전승·관용·창작 중 하나로 확정
- 전승·관용 판정의 근거 기록
- 공통 무공과 우연한 동명 항목 구분
- 세력별 규모와 카테고리 지시 재검토
- 대표 무공 3~5개 재선정
- 1차의 판단 보류 항목 처리

#### 권장 필드

```yaml
origin: 전승
origin_source: 실제 전통 또는 관용 용례를 확인한 출처
shared_with: [hwasan, mudang]
decision_note: 공통 무공으로 유지한 이유
```

출처는 독자를 위한 참고가 아니라 `origin` 판정을 다시 확인할 수 있게 하는 작업 기록이다. 창작 항목에는 `origin_source`를 요구하지 않는다.

#### 금지 사항

- 한 줄 설명, 위력, 초식 등 3차 내용을 앞당겨 작성하지 않는다.
- 자료가 없는데 관용으로 추정하지 않는다.
- 명칭 충돌을 해소하기 위해 정전이나 다른 세력 초안을 임의로 변경하지 않는다.
- 비율을 맞추기 위해 origin을 바꾸지 않는다.

#### 통과 조건

- 모든 항목의 origin 판정이 완료됨
- 창작 명칭 중복 0건
- 해결되지 않은 동명 항목이 작업 보고에 명시됨
- 금지 명칭 0건
- 작성자 검토가 필요한 항목이 별도 목록으로 분리됨

### 3차 작업 규칙

#### 목적

각 이름이 무엇을 뜻하는지 구별할 수 있을 만큼만 설명한다. 무공 백과사전을 완성하는 단계가 아니다.

#### 주요 작업

- 모든 심법과 무공에 한 줄 설명 추가
- 대표 무공에만 필요한 범위의 초식 일부 추가
- 같은 문파 안에서 항목별 역할과 차이를 드러냄
- 심법은 마음을 어떤 방향으로 힘으로 바꾸는지 서술
- 무공은 몸의 움직임과 쓰임을 중심으로 서술

#### 설명 형식 예시

```yaml
summary: 좁은 발디딤에서 한 번의 찌르기로 승부를 정하는 검법.
forms:
  - name: 낙매
    hanja: 落梅
    summary: 대표 장면에 필요한 범위에서만 작성한 초식 설명.
```

#### 제한

- 한 줄 설명은 원칙적으로 한 문장으로 제한한다.
- 대표 무공이 아닌 항목의 초식은 만들지 않는다.
- 초식 전체 목록과 절기는 실제 습작에 필요할 때만 추가한다.
- 강함을 등급, 수치, 다른 세력과의 서열로 표현하지 않는다.
- 심법을 내공 운용법이나 에너지 축적법으로 설명하지 않는다.

#### 통과 조건

- 이름만 다른 사실상 같은 설명이 반복되지 않음
- 모든 설명이 해당 세력의 차별화 지시와 연결됨
- 대표 무공 외 초식이 불필요하게 늘어나지 않음
- 등급표, 기의 운행, 소모되는 내공 등 금지 개념이 없음

### 4차 작업 규칙

#### 목적

서사와 인물 설계에 사용할 수 있도록 심·체 좌표와 실패 조건을 구조화한다.

#### 반드시 읽을 정전

- `canon/body-and-mind/01_두개의축.md`
- `canon/body-and-mind/02_관문과문턱.md`
- `canon/body-and-mind/04_마음.md`
- `canon/body-and-mind/05_힘.md`
- `canon/body-and-mind/07_주화입마.md`
- `canon/body-and-mind/09_성격어휘.md`
- `canon/body-and-mind/10_스키마.md`
- 각 문서 frontmatter의 `requires`에 지정된 문서

#### 주요 작업

- 무공과 심법이 요구하는 심·체 방향 정리
- 위력을 단일 숫자가 아닌 조건과 상성으로 기술
- 확정된 정규 어휘 안에서 `traits` 추출
- 해당 심법이나 무공이 무너지는 구체적 조건을 `breaks_on`에 기록
- 불균형과 주화입마 가능성을 정전의 판정 원칙에 맞춰 검토

#### 작성 원칙

- 심·체 수치는 작가용 좌표이며 세계 안의 등급으로 노출하지 않는다.
- 두 수를 합산하거나 평균 내지 않는다.
- 특정 깊이와 검기·검강 같은 발현을 대응시키지 않는다.
- `fit`, `risk`, `drift`의 미확정 규칙을 임의로 만들지 않는다.
- `traits`에 새 어휘가 필요하면 자동 추가하지 않고 작성자에게 보고한다.
- 주화입마 3층은 자동 판정하거나 배치하지 않는다.
- 깊이 8 이상 인물의 생성과는 별개다. 무공을 구조화했다고 고수를 자동 생성하지 않는다.

#### 통과 조건

- 모든 구조화 필드가 정전 스키마와 일치함
- 미확정 항목을 채운 값이 없음
- 수치 합산이나 임의 임계값이 없음
- 새 `traits` 어휘는 모두 작성자 승인 기록이 있음
- `breaks_on`이 일반적인 약점이 아니라 해당 항목의 구조와 연결됨
- 자동 검증 통과 후 작성자가 의미와 상성을 별도로 검토함

### 검증기 확장 방식

하나의 검증기에 차수별 검사를 추가하되, frontmatter의 `phase`에 따라 검사 범위를 결정한다.

```text
phase 1 검사
  └─ phase 2 검사: 중복, origin 근거, 공유 관계
       └─ phase 3 검사: 설명과 대표 초식 범위
            └─ phase 4 검사: 스키마, traits, breaks_on, 미확정 값
```

상위 차수 문서는 이전 차수의 검사를 모두 통과해야 한다. 예를 들어 3차 문서는 1·2·3차 검사를 함께 받는다.

의미 판단이 필요한 항목은 자동으로 통과시키지 않는다. 검증기는 `작성자 확인 필요` 경고를 내고 작업 보고에 같은 항목이 있는지 확인한다.

### 완료 기준

- 각 차수에서 무엇을 추가하고 무엇을 추가하면 안 되는지 명확하다.
- 다음 차수 진입 조건을 사람과 스크립트가 같은 방식으로 판단한다.
- 4차 데이터가 미확정 규칙이나 임의 수치에 기대지 않는다.
- 새 세력 문서를 만들 때 기존 세력과 같은 검토 품질을 재현할 수 있다.

## 4. 진행 현황 자동 생성

### 현재 상태

`README.md`의 진행 현황은 사람이 직접 수정한다. 실제 파일, 검증 결과, 색인 상태가 변해도 README는 자동으로 갱신되지 않는다.

그 결과 다음 항목이 실제 상태와 어긋날 수 있다.

- 작성된 세력 수
- 현재 작업 차수
- 실행 순서상 완료된 군
- 검증기 구현 여부
- 색인 최신 여부
- 검토가 필요한 경고 수

README는 프로젝트의 변하지 않는 목적과 규칙을 설명하고, 변동이 잦은 현황은 별도 자동 생성 문서가 담당하도록 분리한다.

### 권장 구조

```text
.
├─ README.md
├─ reports/
│  └─ 진행현황.md                scripts/report_progress.py가 생성
└─ scripts/
   └─ report_progress.py
```

README의 수동 진행 목록은 다음처럼 짧은 링크로 교체한다.

```markdown
## 진행 현황

현재 단계별 진행률과 검증 상태는 `reports/진행현황.md`를 참조한다.
이 문서는 `python scripts/report_progress.py`로 갱신한다.
```

### 수집할 정보

`report_progress.py`는 문서 본문을 추측하지 않고 frontmatter와 검증 결과만 읽는다.

#### 전체 요약

- 세력 목록에 등록된 대상 수
- 초안이 존재하는 세력 수
- 차수별 세력 수
- 검토 대기, 수정 요청, 승인된 세력 수
- 색인에 들어 있는 전체 항목 수
- 마지막 생성 시각 또는 기준 커밋

#### 실행 군별 현황

```markdown
| 군 | 대상 | 완료 | 미작성 | 검토 필요 | 상태 |
|---|---:|---:|---:|---:|---|
| 1군 | 5 | 4 | 1 | 4 | 진행 중 |
| 2군 | 5 | 5 | 0 | 5 | 선행 검토 필요 |
```

군 구성은 스크립트에 중복 기입하지 않고 기계가 읽을 수 있는 별도 설정이나 `specs/세력별_차별화지시.md`의 구조화된 데이터에서 가져온다.

#### 검증 현황

- 통과·실패 문서 수
- 경고가 있는 문서와 경고 요약
- 예상 창작 비율에서 20%p 이상 벗어난 세력
- 해결되지 않은 동명 명칭
- 색인이 최신인지 여부
- 세력 목록에는 있으나 초안이 없는 대상
- 초안은 있으나 세력 목록에서 찾을 수 없는 대상

### 명령 인터페이스

```bash
python scripts/report_progress.py
python scripts/report_progress.py --check
python scripts/report_progress.py --stdout
```

- 기본 실행: `reports/진행현황.md`를 재생성한다.
- `--check`: 파일을 쓰지 않고 현재 보고서가 최신인지 확인한다.
- `--stdout`: 파일을 쓰지 않고 생성 결과를 표준출력으로 보여준다.

`build_index.py --check`와 마찬가지로 `--check`는 최신이면 종료 코드 0, 오래됐거나 불일치가 있으면 1을 반환한다.

### 생성 문서의 원칙

- 자동 생성 영역을 손으로 수정하지 않는다.
- 판단이나 향후 계획을 자동으로 확정하지 않는다.
- 경고는 숨기지 않되 오류와 구분한다.
- “다음 작업”은 규칙에 따라 하나만 계산한다.
- 작성자 결정을 요구하는 항목은 별도 절에 모은다.
- 생성 결과는 같은 입력에서 항상 같아야 하므로, 생성 시각을 넣는다면 비교에서 제외하거나 별도 메타데이터로 관리한다.

### 작업 절차와 연결

세력 문서를 변경한 뒤 실행하는 순서를 다음처럼 확장한다.

```text
1. 대상 문서 검증
2. 무공 색인 재생성
3. 전체 세력 문서 검증
4. 진행 현황 재생성
5. 색인과 진행 현황 최신성 확인
```

커밋 전 확인 명령은 다음 형태가 된다.

```bash
python scripts/validate.py --all
python scripts/build_index.py --check
python scripts/report_progress.py --check
```

### 완료 기준

- README와 실제 파일의 진행 상태가 따로 노는 문제가 재발하지 않는다.
- 어떤 세력이 어느 차수와 검토 상태에 있는지 한 문서에서 확인할 수 있다.
- 정해진 군별 실행 순서를 벗어난 상태가 자동으로 표시된다.
- 커밋 전에 색인과 진행 보고서의 최신성을 명령으로 확인할 수 있다.

## 권장 적용 순서

네 보완안은 다음 순서로 적용하는 것이 안전하다.

1. **상태와 차수 분리** — 이후 자동화가 읽을 공통 스키마를 먼저 정한다.
2. **자동 생성 색인 분리** — 새 상태 스키마를 색인의 출처 정보에 반영한다.
3. **2~4차 규칙 작성** — 차수별 입력과 산출물을 확정한다.
4. **진행 현황 자동화** — 앞에서 확정한 상태와 규칙을 읽어 보고서를 생성한다.

각 항목은 별도 변경 단위로 진행한다. 한 번에 모두 바꾸면 문서 경로 변경, frontmatter 변환, 검증기 수정이 섞여 문제의 원인을 찾기 어렵다.

## 적용하지 않는 범위

이 보완 작업은 다음 내용을 자동으로 결정하지 않는다.

- 초안을 정전으로 승격하는 결정
- 미확정사항의 해소
- 세력별 설정의 내용 검토
- origin의 역사적·관용적 타당성에 대한 최종 판단
- 심·체 배치와 주화입마의 서사적 승인

자동화는 누락과 형식 오류를 찾는 역할만 맡는다. 설정을 사실로 승인하는 권한은 계속 작성자에게 둔다.
